## `hard_negative_bases.jsonl` — current, additional to the 100 above

The 20 pilot HARD_NEGATIVE base instances (T11 Phase 1), generated by
`generators/hard_negatives.py` under `guidelines_version: "0.16"`. **Additional to**
`base_instances.jsonl`, never merged into it — `PROJECT_SPEC.md` §12.2: *"20
hard-negative bases (not part of the 100)."* First write; no prior version exists to
preserve.

Every record: `base_kind: "HARD_NEGATIVE"`, `pii: []`, no `entities`/`distractors` keys
(those are derived-record-only fields, guidelines.md §13.4 — a base instance never
carries them, for either `base_kind`), and a populated `hard_negative_decoy`
(`decoy_class`, `value`, `surface_type`, `actual_role` — guidelines.md §13.12, OQ-046)
persisting the construction ground truth a later derived-record generation phase will
read.

Decoy-class distribution follows the frozen §13.9 quota exactly: `NUMERIC_SHAPE` 5,
`ALNUM_SHAPE` 5, `NAME_AS_PLACE` 4, `HANDLE_SHAPE` 3, `PARTIAL_PII` 3, `ORG_AS_PERSON` 0
(deferred from Pilot v0.1 per §13.8 — no base of this class exists in this file or
anywhere else). IDs `NEG_001`–`NEG_020`, permanent, verified not to collide with any of
the 100 `base_instances.jsonl` IDs.

Two implementation-level choices, disclosed in `generators/hard_negatives.py`'s own
module docstring (not new governance freezes): (1) `NUMERIC_SHAPE` cycles across
PHONE/AADHAAR/BANK_ACCOUNT-shaped values and `PARTIAL_PII` cycles across
AADHAAR/BANK_ACCOUNT-shaped values, in the order guidelines.md §13.8 itself lists them
— §13.8 explicitly allows either shape without specifying a mix; (2) `scenario.domain`/
`scenario.purpose` use one uniform value across all 20 (`"customer_support"` /
`"hard_negative_context"`) — no per-decoy-class scenario allocation is frozen anywhere,
unlike positives' §12.3 domain-distribution matrix.

**Phase 2 (derived-record generation for these 20 bases) has not run.** No
hard-negative derived record exists in `data/generated/language_realizations.jsonl` or
anywhere else.

**Do not use this file for anything.** It is the dataset generated after OQ-007 but
*before* T07 (transliteration) existed — every `person_context.name_deva` is `null`,
and there is no `generator_version` field at all (schema didn't require it yet).

required by `schemas/base_instance.schema.json`, OQ-020) is absent here, and every
`person_context.name_deva` is `null` here instead of its T07-populated value.
`base_id`, `base_kind`, `pii` (including every `base_pii_value`), `scenario`,
`address_structure`, `canonical_text`, `synthetic`, and `person_context.name` are
byte-identical between the two files for all 100 records (verified by diff — see
`annotation/open_questions.md` OQ-020/OQ-021's resolution notes).
